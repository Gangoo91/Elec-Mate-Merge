## Block 2 — Correctness: the app loses or misstates what was typed

These are the findings that damage a certificate or the electrician's credibility. All are
small and contained. This is the real work of the day.

### 2.1 — WITHDRAWN. The notes are read; the guard was wrong

This was the plan's headline item and it was based on a false finding. All eight notes fields
are read via `` const note = (key) => get(`${key}Notes`) `` (`eicrJsonFormatter.ts:921`), with
21 such calls. Nothing is discarded.

Replaced by **D20**: `check:cert-mapping` decides "read" by literal substring search
(`scripts/check-cert-mapping.mjs:313`), so it false-positives on any runtime-built key. All 8
EICR "unread" fields are that pattern. Worth fixing the guard — it is the net that catches
dropped fields, and a net that cries wolf gets ignored — but it is **not** a certificate
defect and does not belong in Block 2.

### 2.2 — D2: boilerplate observations can reach a signed certificate (High)

Marking an item C2 pre-fills *"Item requires attention - inspection outcome not
satisfactory"* and *"Investigate and rectify as required to comply with BS 7671"*. Both print
verbatim. A coded defect that describes no defect is a professional-risk defect.

Leave the observation and recommendation **blank**, and add "observation text written" to the
pre-issue checklist so it cannot be issued empty.

### 2.3 — D12: AI cites the wrong special location (High)

For a domestic bathroom the assistant returned six BS 7671 refs; **four were from the wrong
Part 7 section** — `710` medical locations, `702` swimming pools, `740` fairgrounds,
`714` outdoor lighting. Only `701.411.3.3` and `415.1.2` were apt. Verified against
`bs7671_facets`.

Cause is retrieval scope: "supplementary protective equipotential bonding" appears in every
Part 7 section. The primary action is **"Use these"**, plural.

Fix is a filter, not a rewrite: drop any `7xx` reference whose section does not match the
location in scope; keep the Part 4 generals.

### 2.4 — R₂ column binds to the wrong field (High)

`ContinuityCells` binds the R₂ column to `ringContinuityLive` ("temporary field"), while
`TestResult.r2` exists, is documented as "R₂ only (Ω)" and **nothing writes it**. Anything
reading `r2` sees empty on every certificate. Pick one and remove the other.

### 2.5 — Bulk infill ignores its own board scope (High)

Sets `activeBoardId` on open, then maps **every circuit on every board**. Also has **no
spare-way guard**, unlike its sibling `handleBulkFieldUpdate`. Field list duplicated across
two files; both copies include the dead `r2` and both omit `ringContinuityLive`.

Given row multi-select + "Set a field" now does this job board-scoped and spare-guarded off a
single column registry, the honest options are fix or retire. **Recommend retire.**

### 2.6 — D17: lapsed credentials accepted silently (High)

Registration expiry and insurance expiry both accepted `2019-01-01`. No `min`, no warning. An
electrician with seven-year-lapsed insurance can print that date on a certificate.

Warn on any expiry in the past; block at the issue gate.

### 2.7 — D14: invalid email accepted silently (High)

`definitely!not@an@email` stored. The browser knows — `validationMessage: "A part following
'@' should not contain the symbol '@'"` — but there is no `aria-invalid`, no border change and
no message. That is the address the certificate is emailed to.

## Amendment support — settled, not a work item

An earlier draft of this plan called A3 support "the single biggest commercial gap".
**That was wrong on two counts** and is recorded here so it does not get re-raised:

1. **The picker already exists.** `InspectionDetailsSection.tsx:877` — "BS 7671 edition",
   four options, A1 (2020) through A4 (2026), writing `bsAmendment`.
2. **Per-amendment rules are deliberately out of scope.** Founder decision, 7 Aug: we
   validate against **A4 only**. The tables and rules we rely on do not differ materially
   between amendments, and a periodic inspection is in any case carried out against the
   current edition. The field records the edition the installation relates to — it is not a
   claim that our checks change with it.

So `bsAmendment` printing a label and driving nothing is **correct behaviour**, not a defect.
`ELE-1490 / 1491 / 1492` should be closed or re-scoped rather than built.
